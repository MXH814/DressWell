# 穿好第三周需求评审清单

这次请大家帮需求分析负责人核对调研结论和需求草稿：哪些需求应该保留，业务规则是否准确，用户应该看到什么结果。评审时**只需回复有意见的编号和修改建议**。

## 调研结论有没有写偏

| 编号 | 请核对的结论 |
| --- | --- |
| R1 | A01 用已有夹克的成衣尺寸帮助选码。A04 的白衬衫尺寸合适，却在不同光照下发现透光。尺寸对照应说明依据，透光和实际穿着效果由用户试穿核对。 |
| R2 | A02 发现原本要搭的旧裙子已经不合穿，A06 换回常穿的帆布鞋后发现裤脚蹭地。A05 的旧订单链接已下架，同品牌门店店员凭订单款号找到同款，并核对了领标和尺码。这支持保留按款号查找的入口；线上能否查到同款由 UC-09 验收。 |
| R3 | A03 遇到其他色码的起售价。慢慢买也只核实到目标外套一条已失效的历史活动，未核实到当日可买报价。当前比价要核对款号、颜色、尺码、库存和有效状态。 |
| R4 | Acloset 1.0.9 桌面扩展实测到邮箱和密码输入页，没有填写凭证。录入、保留色码、试搭和找回均未实测，官网描述单独作为资料参考。 |
| R5 | Outfity 在同一设备刷新后，可从计划页找回已保存的搭配。切换到个人衣橱时，需要重新选外套图片和类别。DressWell 的待验收目标是确认留用后复用原图片、已核实规格和原搭配。 |

以上来自 6 场真人访谈和 3 款竞品的一组同任务测试。如果发现结论和原记录或截图不一致，请指出证据编号和要改的表述。

## 逐条看功能验收条件

### 选款、选码与比价

| 用例 | 试一下这个场景 | 应该看到的结果 |
| --- | --- | --- |
| UC-01 按目标规格比价 | 分别验证 A03 的两店例、独立的双平台有效快照、单个平台有一店或多店、零有效报价，以及优惠资格或运费未知。完整 Given / When / Then 见 [SRS](requirements-srs.md#uc-01-跨平台与降级验收)。 | 两店例按 149／155 元排序，其他色码不纳入。双平台例按 159／167 元排序并显示平台、来源和核验时间。仅一个平台时标明限制；同平台多店可以比价，但只算一个平台。零条显示无有效报价。待核实金额退出有效排序。 |
| UC-02 用旧衣对照尺码 | 旧夹克腋下平铺宽 57 cm，新夹克 L 码成衣胸围 114 cm，按胸围对照。 | 显示 57 × 2 = 114 cm，指出 L 码胸围与参考衣物一致，并提醒肩宽、袖长仍待核对。 |
| UC-03 识别不能比较的尺寸 | 旧衣记录的是成衣尺寸，商品只给建议人体胸围或未注明口径。 | 说明缺少可比数据，暂停给出基于该项的尺码建议。 |
| UC-06 保存待购候选 | 用商品截图或链接保存一件上衣，再重新打开。 | 能找回候选及已保存的出处。候选尚未进入可穿衣橱。 |
| UC-09 凭款号找回同款 | 旧链接失效，改用已知款号搜索。 | 有匹配时显示结果；没有时说明未找到，并保留查询款号。 |
| UC-10 识别过期或待核实报价 | 一条活动已过期，另一家只显示无法核实规格的起售价。 | 分别显示「已失效」「待核实」和来源，两条都不参与当前有效报价排序。 |
| UC-17 维护失效报价 | 有权限的商品数据维护者确认商家链接失效并更新状态。 | 报价退出有效排序，来源及状态变更仍可查看。 |

### 衣橱和搭配

| 用例 | 试一下这个场景 | 应该看到的结果 |
| --- | --- | --- |
| UC-04 登记衣物 | 用照片录入一件夹克并选择类别。 | 衣橱新增一个单品，能查看和修改类别。 |
| UC-05 排除当前不可穿的衣物 | 把一条裙子标为不可穿，再请求搭配。 | 推荐结果不包含这条裙子，仍可在衣橱中管理它。 |
| UC-07 用已有衣物试搭 | 选一件待购上衣、个人衣橱中的裤子和鞋，搭成一套并保存。 | 能找回原来的组合，待购单品和已有单品状态可区分。 |
| UC-08 只换不合适的一件 | 锁定裤子，再要求换鞋。 | 裤子保持原选择；有可用鞋则给出替代，没有则提示缺项。 |
| UC-11 提示实际试穿核对 | 白衬衫尺寸合适，但缺少透光资料，查看面试搭配。 | 尺寸对照与试穿提醒分开展示，透光性标为待确认。 |
| UC-15 按场合和手填条件搭配 | 用户填写通勤场合和“下雨”“需要步行”等条件，再请求搭配。 | 从可穿衣物生成方案，说明如何照顾这些条件。无法满足时说明缺什么。 |
| UC-21 查看公开示例 | 未登录访客先打开公开示例，再尝试用获得的地址访问私人衣橱或搭配。 | 能打开示例，私人衣橱、搭配及相关照片均不返回。 |

### 收货、留用与反馈

| 用例 | 试一下这个场景 | 应该看到的结果 |
| --- | --- | --- |
| UC-12 标为已买待收 | 给带有购前搭配的候选标记「已买待收」。 | 状态更新，原方案还能打开，候选暂不进入可穿清单。用户是否会主动维护该状态仍是待验证假设。 |
| UC-13 留用后找回原搭配 | 确认留用一件有已核实规格和购前搭配的候选，再打开原方案。 | 同一件候选成为可穿衣物，原图片、规格和搭配均可找回，无需重新录入。 |
| UC-14 退货后退出推荐 | 分别从“已买待收、试穿后直接退货”和“确认留用后退货”两条路径登记退货，再生成搭配。 | 两条路径均能查看已退货状态，后续可穿推荐均排除该件。 |
| UC-16 保存试穿反馈 | 对牛仔裤和帆布鞋的组合记录「裤脚蹭地」，随后重新打开。 | 能看到反馈，以及反馈对应的两件单品。 |

### 性能、安全与故障恢复

| 用例 | 试一下这个场景 | 应该看到的结果 |
| --- | --- | --- |
| UC-19 查价响应时间 | 预热后，5 个同优惠资格的会话每轮均发起 API 查询。从点击到有效列表完整显示计时，共 4 轮 20 次。 | 20 次均仅列平台 B 159 元、平台 A 167 元，顺序与来源正确，且至少 19 次不超过 2 秒。任一错误、10 秒超时或达标次数不足即失败。 |
| UC-20 私人照片访问 | 用户乙已登录，并拿到用户甲的私有衣物照片标识。乙先请求图片，随后甲请求同一张图。 | 乙拿不到照片内容，甲能正常查看。 |
| UC-22 中断后找回搭配 | 服务端确认保存后断网至少 10 秒，期间结束应用进程。恢复网络，用原账号重开，从点击「已保存搭配」计时到原搭配完整可见，含打开详情的耗时，共 3 轮。 | 3 轮均不超过 30 秒；原搭配只出现一次，标识、规格、三件单品和状态与中断前一致。有一轮无法进入列表、超时、重复、缺项或状态不同即失败。 |
