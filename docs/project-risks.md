# 穿好项目风险清单 · 评审草案

建议第一轮优先验证报价来源。一次选错颜色、尺码或优惠资格，就可能把更贵的店排在第一位；如果拿不到第二个平台的有效报价，即使界面能显示价格，也无法回答用户“去哪买”。胡知鱼在启动评审中提出了这个问题，后续调研和样本给出了可以检查的例子。[启动评审](https://github.com/MXH814/DressWell/pull/4#pullrequestreview-5988751795) · [选题 Issue](https://github.com/MXH814/DressWell/issues/1)

## 已有证据

- 访谈 A03 记录了一次购买：同款黑色 M 码在甲店券后 149 元、乙店 155 元，乙店的 139 元起对应灰色。这说明用户为什么要逐项核对；它是受访者的购买经历，两家店分属不同平台尚未得到验证。[访谈 A03](https://github.com/MXH814/DressWell/blob/234b870a3088a4ebd7c910f086100cdcb648a051/docs/用户调研访谈纪要.md#a03)
- 竞品实测 C01 找到一条符合款号和色码的历史活动，能复算出 1,427.86 元，但活动已失效；测试当天确认可买的目标规格报价为零。商品样本 PR 的 500 条记录也都来自苏宁，适合验证字段读取。跨平台可行性仍须另取证。[竞品实测记录](https://github.com/MXH814/DressWell/blob/234b870a3088a4ebd7c910f086100cdcb648a051/docs/竞品任务实测.md) · [样本 PR #12](https://github.com/MXH814/DressWell/pull/12)

## 建议的跟进方式

表中岗位、检查节点和处理方案供成员评审。每项由实际认领人记录样本或测试链接、核验结果和下一步；组长在迭代回顾时更新仍未解决的项目。发现风险时即可开 Issue 跟踪，关闭时保留触发过的反例和复测结果。

| 风险及影响 | 建议牵头岗位及节点 | 怎样发现问题 | 触发后的处理 |
| --- | --- | --- | --- |
| R1 · 不同平台缺少可比报价，或错误推荐最低价 | 商品数据负责人在 v0.1 期间试查，测试负责人独立复算；确定 v0.2 支持范围前评审 | 选少量有明确款号、颜色、尺码的商品，在两家不同平台逐条保存来源、核验时间、库存、标价、券资格、运费。用同规格有效报价复算排序，再用异色、失效活动或未知运费各试一次。 | 只有一条有效报价时展示其来源及时间，提示尚缺可比报价；零条时说明原因。失效或无法算清到手价的记录退出有效排序。演示历史快照时标出核验时间，依据反复取得的样本决定覆盖范围。 |
| R2 · 商品尺码口径混用，用户收到衣物后不合身 | 需求分析与商品数据负责人在 v0.2 尺码对照开发前核验 | 用旧夹克平铺宽度、新衣成衣胸围和商家建议人体胸围分别试算，检查是否说明测量部位及单位。访谈中，胸围能对照也无法判断透光性。[A01、A04 纪要](https://github.com/MXH814/DressWell/blob/234b870a3088a4ebd7c910f086100cdcb648a051/docs/用户调研访谈纪要.md) | 只对口径可比的项目给出差值和依据；资料缺失时提示补量或试穿。 |
| R3 · 私有衣物照片可被其他用户打开 | 架构与测试负责人在 v0.1 开放照片功能前验证 | 用两个账号和一个访客，依次以本人、他人、未登录身份访问同一私有图片地址，核对实际返回内容。[安全故事 #32](https://github.com/MXH814/DressWell/issues/32) | 出现越权就暂停发布相关功能，修复资源访问校验，并以原地址复测；演示仅使用有权公开的示例图。 |
| R4 · 搭配已提示保存，重开却丢失；留用或退货后显示了错误单品 | 后端开发与测试负责人在 v0.2 保存流程和 v0.3 状态联调时验证 | 保存含待购款的搭配，断网关闭后重新进入；再分别走留用和退货，核对规格、单品数与状态。正常刷新的竞品观察不足以验证断网恢复。[恢复故事 #35](https://github.com/MXH814/DressWell/issues/35) · [退货故事 #27](https://github.com/MXH814/DressWell/issues/27) | 保存尚未成功时明确提示可重试。出现丢失、重复或已退货单品仍被推荐时，暂缓交付相关路径，修复后按原步骤复测。 |
| R5 · 外部集成迟迟未选定，迭代末才发现无法接通 | 架构负责人在首轮计划内提出方案，组长确认范围 | SRS 草稿将外部接入留给架构负责人。建议从课程认可的集成中选一项，例如与私有衣橱相衔接的第三方登录，用测试账号实际走通授权、回调及取消授权。核验所需账号权限与部署条件。[SRS 范围说明](https://github.com/MXH814/DressWell/blob/234b870a3088a4ebd7c910f086100cdcb648a051/docs/requirements-srs.md) | 记录具体阻碍及最晚重试节点；若接入条件不具备，尽早改选另一项课程认可的集成并复测。模拟回调只用于开发测试。 |

建议 R1 按两层交付：能用两个不同平台的有效快照复算一次价格时，优先交付带时间戳的指定规格比较；进一步验证可持续获取和更新后，再承诺更新频率。若连一组有效快照都取不到，保留单源核价与不足提示，在迭代回顾注明跨平台目标仍未达成。

评审时，请成员确定双平台取样和独立复核由谁承担、是否接受上述降级范围，以及其余风险何时可以放行。实际认领、修改理由和复测结果记入关联 Issue。这份草案所引用的已执行工作限于上面列出的访谈、实测和样本观察。
